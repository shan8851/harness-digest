### 1. [learn-harness-engineering](https://github.com/walkinglabs/learn-harness-engineering)
*repo · 15 min · harness design · 9/10*

Agents fail on real repos from a weak environment, not a weak model; this course teaches a file-based harness covering instructions, state, verification, scope and session lifecycle, with projects and templates.

**How it works**
- Add AGENTS.md as a short map to deeper docs, rather than one giant instruction file.
- Keep feature_list.json as machine-readable scope so the agent works on exactly one unfinished feature.
- Run init.sh at session start to install, verify and health-check before any work begins.
- Log progress in a markdown file and commit clean state so the next session resumes exactly.
- Count only passing tests, lint and type checks as evidence; the agent records proof before claiming done.

**Steal this:** Before your next multi-session agent task, drop in AGENTS.md, init.sh, feature_list.json and a progress log, and require the agent to update them before stopping.

**Go deeper if:** you're already running coding agents on real repos and want templates, a harness audit script and projects comparing weak versus strong harnesses.

> "The MODEL decides what code to write. The HARNESS governs when, where, and how it writes it."

### 2. [Stop trusting your AGENTS.md: the drift-check that makes it a contract](https://dev.to/veaceslav/stop-trusting-your-agentsmd-the-drift-check-that-makes-it-a-contract-47pc)
*blog · 7 min · verification · 9/10 · 3 Nov*

A lean AGENTS.md is still just prose that quietly goes stale, so tag each rule with a marker and run a CI script that fails when rules and checks fall out of sync.

**How it works**
- Put an invisible HTML marker like <!--check: single-lockfile--> next to each rule in AGENTS.md, so the prose stays readable.
- A small Node or Python script extracts marker ids and maps each to a verification function returning pass, fail, or offending files.
- Two-way binding: a marker with no mapped check fails, and a check with no marker fails.
- Run it as its own GitHub workflow on pull requests and pushes, exiting 1 on any drift.
- Make checks inspect real code, such as actual imports, rather than only config keywords, and update rules in the same PR as the change.

**Steal this:** Before your next AGENTS.md edit, add a check marker to each rule and write a short script that fails CI when any marker lacks a mapped check, or the reverse.

**Go deeper if:** you're tired of agents quietly violating conventions in your instruction file and want a concrete CI pattern plus the failure modes of building it.

> "A rule that nothing can break isn't a rule; it's a suggestion the next agent will politely decline."

### 3. [markhazlett/agent-harness: Portable coding agent harness](https://github.com/markhazlett/agent-harness)
*repo · 8 min · harness design · 8/10*

Coding agents drift into destructive or sloppy habits, so this repo wraps one in hooks that block risky commands, skills with fixed rules, and a weekly plan-build-ship workflow.

**How it works**
- A bash-guard hook blocks commits on main, --no-verify, sed -i on source, and rm -rf on source dirs.
- A protected-files hook stops edits to .env, hook scripts, settings.json and the lockfile, guarding the guards.
- Session-start and stop hooks inject branch and handoff notes, then run tests and typecheck if source changed.
- Verification skills carry a one-sentence Iron Law plus a Rationalization Table of real excuses the model used under pressure.
- A read-only validator agent runs tests and lint, and /orchestrate loops builders and validator up to 3 cycles.

**Steal this:** The next time an agent talks itself out of a test or gate, record its exact excuse in a Rationalization Table inside the relevant skill, next to a one-line Iron Law.

**Go deeper if:** you're building your own hooks, skills and guardrails and want a complete, working example to copy from.

> "Hooks are the one exception (they catch destructive shell commands), and they too are configurable."

### 4. [loop-harness: scheduled agent loops with worktree isolation and a second-agent verification gate](https://github.com/lSAAGl/loop-harness)
*repo · 6 min · harness design · 8/10*

Unattended agents risk shipping unchecked work, so this harness has the primary agent only stage outputs in an isolated worktree, and a skeptical second agent must pass them before anything is pushed or posted.

**How it works**
- A scheduler wakes each loop on a cadence and gives a Claude session a task-specific skill file.
- Write loops run in a fresh git worktree on their own branch, never touching your checkout.
- The primary agent can't push or post; it stages commits, a PR body, or outbox action files.
- A second read-mostly claude session inspects the diff, runs cheap checks, and must print VERDICT: PASS.
- Each skill ends with a RESULT line whose stable item IDs feed a state file for deduplication, so reruns are safe.

**Steal this:** Before your next unattended agent job, split it into a stage step that writes outputs to files and a separate verifier session that must print an explicit PASS before anything ships.

**Go deeper if:** you're running agents on a schedule or in CI and want a small shell-based template for isolation, verification gates and idempotent state.

> "You don't prompt Claude ; loops do."

### 5. [How We Optimized Browser Use for Deep Agents](https://www.langchain.com/blog/how-we-optimized-browser-use-for-deep-agents)
*blog · 10 min · harness design · 8/10 · 3 Nov*

Browser agents burn context and turns because tools return huge page dumps one step at a time; code-mode tools, compact snapshots and trace-driven fixes cut cost and time while accuracy held.

**How it works**
- Let the agent write one code snippet that chains many browser steps, so intermediate page content stays in variables, not context.
- Return a trimmed accessibility tree with IDs on interactive elements instead of raw HTML or screenshots.
- Trim output at the source: capping snapshots after the fact just made agents refetch the page.
- Read traces to spot waste, such as fixed 8-second sleeps, then end sleeps once the page is quiet for 500 ms.
- Run evals on every change before keeping it, comparing setups side by side as experiments.

**Steal this:** The next time your agent's tool returns bulky output, read a few traces for repeated waste, change the tool to return less or batch steps, and rerun your evals before keeping the change.

**Go deeper if:** you're building or tuning tools for a long-running agent and want measured before-and-after numbers on cost, turns and accuracy.

> "Traces show where the agent wastes steps and tokens, and evals tell you whether a change helped."

### 6. [Your agent tool guard probably fails open. One minute to tell.](https://dev.to/dekita/your-agent-tool-guard-probably-fails-open-one-minute-to-tell-3odc)
*blog · 6 min · harness design · 8/10 · 3 Nov*

Agent tool guards often fail open because the orchestrator proceeds unless told to block; probing the guard with crash, silent, and odd-input cases shows which paths actually refuse a call.

**How it works**
- Exit code 2 is the only blocking code in Claude Code hooks; crashes, exit 1 and a missing script all let the call proceed.
- Make the guard raise once, print nothing once, and exit 2 once, then check the transcript for which refused.
- Pipe variant command strings into the hook: quoted paths, git -C, quoted subcommand names, and empty input, printing each exit code.
- Put the deny where the side effect is decided, since settings edits only gate operations that haven't resolved policy yet.
- Turn each permission layer off in turn to find which one actually decides, and fail closed whenever the guard can't reach a verdict.

**Steal this:** Before you trust your next PreToolUse hook, pipe the five sample command strings into it and confirm that crash, empty input and a quoted-path variant all exit 2.

**Go deeper if:** you're running coding agents with hooks or deny rules and want to know whether those guards really stop anything.

> "A guard that "crashes loudly" is a guard that fails open loudly."

### 7. [Claude Code Stop Hook: Block Early Exit Without Loops](https://dev.to/aobaworks/claude-code-stop-hook-block-early-exit-without-loops-416l)
*blog · 12 min · verification · 8/10 · 2 Nov*

Agents often declare done too early. A Stop hook runs your real check, such as tests passing, blocks with a specific reason while it fails, and gives up after a capped number of retries.

**How it works**
- Register a command hook under Stop in .claude/settings.json; Stop takes no matcher, so it fires on every finished turn.
- The script reads session_id and stop_hook_active from stdin, then runs npm test and checks that the output file exists.
- On failure it prints JSON with decision block and a reason containing the last 30 lines of test output.
- A per-session counter file caps retries at about 3, then exits with a systemMessage and logs GAVE_UP for cron to grep.
- Build the JSON with jq, send test output to a file not stdout, and pipe sample input in by hand to test.

**Steal this:** Before your next unattended or overnight run, copy the verify-before-stop.sh script, swap in your real done check, set a retry cap of 3, and add a grep for GAVE_UP in your wrapper.

**Go deeper if:** you're running Claude Code unattended in cron or CI and need a deterministic, budget-capped done check, or you're debugging a Stop hook that won't fire.

> "A Stop hook lets a script that you control decide whether the work is actually done."
