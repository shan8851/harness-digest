### 1. [mattpocock/skills](https://github.com/mattpocock/skills)
*repo · 8 min · harness design · 9/10*

Agents misread intent, ramble, ship broken code and pile up complexity; a set of small, composable skills adds grilling sessions, a shared glossary, TDD loops and design checks to counter each failure.

**How it works**
- Run /grill-me or /grill-with-docs first so the agent interviews you until every branch of the plan is settled.
- Record project jargon in a GLOSSARY.md and ADRs, so the agent uses one precise term instead of long phrases.
- Use the /tdd skill for red-green-refactor, writing a failing test first so the agent always gets feedback.
- Use /diagnosing-bugs to build a red feedback loop, then minimise, hypothesise, instrument, fix and add a regression test.
- Run /code-review as parallel sub-agents, one checking repo standards and one checking spec fidelity, so neither contaminates the other.

**Steal this:** Before your next feature, have the agent grill you with a /grill-with-docs style interview and write the agreed terms into a GLOSSARY.md it reads in later sessions.

**Go deeper if:** you're running coding agents daily and want to borrow a tested, editable set of skill files rather than adopt a heavy process framework.

> "The fix for this is a grilling session - getting the agent to ask you detailed questions about what you're building."

### 2. [Cutting our inference bill by 68% by being obsessive about optimization](https://blog.cloudflare.com/obsessive-inference-optimization/)
*blog · 12 min · real setups · 9/10 · 19 Oct*

An AI code reviewer's cost per review passed $2 as models and context grew; logging each session's first request, then fixing cache prefixes and call counts, cut it 68% without losing real findings.

**How it works**
- Log token usage and a hash of the system block for each session's first LLM call to see cache misses.
- Split the system prompt at a marker so shared tool and agent text gets its own cache breakpoint.
- Strip repository-specific content from before that breakpoint, and put reference files in the prompt instead of tool reads.
- Remove tools reviewers can't use, read files in parallel, skip reviewers with nothing new, and stop after the review posts.
- Check quality by comparing findings authors acted on, and by blinded model judges, before moving models or effort.

**Steal this:** Before your next agent cost review, log a hash of each session's first system block plus its cache read/write tokens to find whether shared prefixes are actually hitting the cache.

**Go deeper if:** you're running agents at volume and want a worked example of cache-prefix fixes and checking that cheaper settings still find real problems.

> "the two things we’d check first are whether each session’s first request actually reads from the cache"

### 3. [How To Use Decision Models for Evals](https://hamel.dev/blog/posts/decision-model-evals/)
*blog · 12 min · verification · 8/10 · 20 Oct*

Cheap decision-model judges are often run at the default 0.50 threshold, which can waste performance; tune the threshold on labeled traces, then check calibration and cost before choosing a model.

**How it works**
- Label a set of traces pass/fail, then save each model's failure probability for every trace.
- Set minimum precision and recall for your use case, such as 80% each, and rule out models that miss them.
- Tune each model's threshold with stratified five-fold cross-validation, picking on training splits and measuring on held-out traces.
- Check calibration with a reliability plot and Brier score; apply Platt scaling only if it measurably improves them.
- Compare tuned F1 against cost per 100 eval runs to find the cheapest model that clears your bar.

**Steal this:** Before you next adopt a cheap LLM or decision-model judge for automated evals, save its scores on labeled traces and ask a coding agent to cross-validate a threshold against minimum precision and recall instead of using 0.50.

**Go deeper if:** you're replacing an expensive LLM judge with a cheaper classifier and want a rigorous way to compare thresholds, calibration and cost.

> "Using this default without checking it against your data can give you subpar results."

### 4. [The Thin Orchestrator: How We Made Our AI Agents More Reliable by Giving the Router Less to Do](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)
*blog · 6 min · harness design · 8/10 · 19 Oct*

One agent loaded with all domain knowledge started hallucinating and mixing up subsystems; a thin deterministic router that delegates reasoning to isolated, specialized subagents made the system far more reliable.

**How it works**
- A deterministic orchestrator classifies intent, gathers fields, checks reliability gates, and delegates, but never reasons about code itself.
- Fourteen subagents each hold only their own domain knowledge, so one data source's patterns can't leak into another's.
- Every request follows a fixed 7-step protocol; only the delegation step uses LLM reasoning, inside an isolated subagent.
- Workflow templates sequence the same subagents in different orders, so new use cases need no new agent code.
- Knowledge files load on demand at runtime, so updates take effect in the next session without redeploying the orchestrator.

**Steal this:** Before your next multi-step agent build, split every component into routing (deterministic code) or reasoning (isolated subagent), and give each subagent the same instruction-file template: knowledge sources, required inputs, steps, troubleshooting.

**Go deeper if:** you're running one big agent with a sprawling context that confuses concepts across subsystems, and want a concrete structure for splitting it up.

> "The agent had everything it needed. That was the problem."

### 5. [Your CLAUDE.md Is Too Long: What to Cut So Claude Code Follows It](https://dev.to/promptmaster/your-claudemd-is-too-long-what-to-cut-so-claude-code-follows-it-5713)
*blog · 6 min · harness design · 8/10 · 19 Oct*

Bloated CLAUDE.md files get their rules ignored, so cut every line that fails a simple test and move the rest into hooks, skills, path-scoped rules or a local file.

**How it works**
- Ask of every line: would removing this cause Claude to make mistakes? If not, delete it.
- Delete personality prompts, generic advice and folder tours that Claude can learn by reading the code.
- Move formatting rules into a PostToolUse hook that runs prettier after every Edit or Write.
- Move multi-step procedures into skills, and area-specific rules into .claude/rules files with a paths field.
- Put personal settings in a gitignored CLAUDE.local.md, then check /context and run /doctor prompt-audit.

**Steal this:** Before your next change to CLAUDE.md, run the one-line test on every line and move style rules into a formatter hook, migration recipes into a skill, and API rules into a path-scoped rule.

**Go deeper if:** you're watching Claude Code ignore rules in a CLAUDE.md that has grown past a couple hundred lines and want a concrete pruning checklist.

> "Would removing this cause Claude to make mistakes?"

### 6. [Code Review After Code Gets Cheap](https://www.oreilly.com/radar/code-review-after-code-gets-cheap/)
*blog · 11 min · lighter review · 8/10 · 16 Oct*

Agent-written pull requests outpace human reading time, so make evidence a condition of acceptance: agree on behavior and blast radius first, then spend review effort where evidence is weak or consequences are serious.

**How it works**
- Before generation, agree the intended behavior, boundary examples and expected blast radius with whoever owns the requirement.
- Ask an agent to compare the spec with the changed files and callers, flagging missing or unexplained behavior.
- Check test assertions against the agreed rule; remove the guarded check temporarily to confirm the test actually fails.
- Attach a short review record: agreed behavior, linked evidence for this revision, extra behavior, blast radius, open questions.
- Scale inspection to blast radius; spot-check changes treated as routine and strengthen checks if gaps keep appearing.

**Steal this:** Before approving your next agent-generated pull request, require a short review record and temporarily disable the key guard clause to prove its test fails.

**Go deeper if:** you're the bottleneck reviewing agent output and want a policy for deciding which changes deserve line-by-line reading.

> "Treat blast radius as a review criterion on its own."

### 7. [How Meta Built Forum With AI-Native Engineering](https://engineering.fb.com/2026/10/15/ml-applications/how-meta-built-forum-ai-native-engineering/)
*blog · 8 min · real setups · 8/10 · 15 Oct*

Agents produce plausible but unverified code, so Meta's Forum team made verification the finish line and changed the codebase and tooling so the agent runs its own plan-build-test loop.

**How it works**
- Count a task as done only when automated tests and visual checks pass, not when it compiles.
- Rules, skills, commands and hooks encode conventions; a repeated agent mistake gets fixed once as a permanent rule.
- Give the agent tools to read the live view hierarchy and list on-screen elements before acting, instead of describing the app.
- Run repeatable stress scenarios (fast scrolling, rapid navigation) so the agent can spot anomalies, reproduce, fix and verify.
- Attach build results, test outcomes and recorded verification sessions to each pull request so engineer sign-off is fast.

**Steal this:** The next time your agent edits the wrong thing, add a tool that lets it inspect real state (like the live UI tree or a config dump) before acting, instead of adding more prompt description.

**Go deeper if:** you're moving from autocomplete-style AI use to agents running full build-test loops and want concrete harness, verification and context practices.

> "What improved quality wasn’t better prompting. It was context."
