### 1. [Tests as data](https://martinfowler.com/articles/tests-as-data.html)
*blog · 25 min · verification · 9/10*

AI agents rewrite their own tests, so developers stop trusting them; moving the contract into readable data files run by a small AI-generated runner makes tests easy to review and to protect.

**How it works**
- Write customer tests as input, expected output and setup in YAML or CSV tables, with no implementation details.
- Draft one sample test in your preferred DSL, then have the agent write the parser and test runner.
- Use an external DSL where assertions are mandatory syntax, so the agent can't write weak or assertion-free tests.
- Protect test data and runner files with read-only permissions, hooks, or a CI check on which files changed per task type.
- Validate the tests with mutation testing and an oracle, such as official manuals or a real system running the same tests.

**Steal this:** Before your next agent-written feature, put the acceptance cases in a YAML or CSV table, have the agent build a small runner for it, and fail CI if that data file changes in a refactoring PR.

**Go deeper if:** you're letting agents write and refactor tests, no longer trust the suite, and want concrete DSL, runner and file-protection patterns to rebuild that trust.

> "In short, prose specs can't be executed; tests can."

### 2. [Long-horizon agents and durable execution](https://martinfowler.com/articles/durable-execution-agents.html)
*blog · 25 min · harness design · 9/10*

Agents that run for days or weeks crash, retry and act on stale facts; wrapping the loop in durable execution and putting business rules in tool code lets them recover safely.

**How it works**
- Route every outside call (model decision, tool, message) through a logged step; after a crash, replay skips recorded steps and rebuilds state.
- Gate tools with an allowed(state) check, so rules like 'no order before approval' live in code, not the prompt.
- Use an idempotency key, such as the PO number, so at-least-once retries don't place duplicate orders.
- Re-check facts before irreversible actions, and have managers approve a price range with an expiry instead of one value.
- Version business rules in state so running tasks finish under the old rule while new ones use the new one.

**Steal this:** Before your next agent tool that does something hard to undo, add a deterministic allowed() precondition and a re-read of the underlying facts inside the tool, rather than trusting the prompt.

**Go deeper if:** you're building agents that wait on people or external systems for days and need crash recovery, retries and safe deploys.

> "This way the business rules that matter are in code, not in the prompt."

### 3. [I stopped babysitting my coding agents. Here's the workflow.](https://code.minimax.io/docs/techblog/coding-agent-workflow-and-skills)
*blog · 14 min · real setups · 9/10*

Running many parallel agents left the author as the bottleneck on decisions and bug-finding, so they switched to one owner agent that proves its work on the real app, checked by a different model family.

**How it works**
- Interview first: core-grill asks only about user-visible choices, then core-spec writes spec.md and verify.md, with checks written before any code.
- A different model family reviews both files read-only in a fresh session; then they are frozen and a draft PR is opened.
- One deliver agent owns the work, keeps a committed plan.md in ExecPlan format, and checks each milestone with a fresh subagent.
- A script, check-delivery.mjs, gates merge: frozen specs unchanged, report covers merged code, verdict PASS, verifier from another model family.
- Decisions and deviations sit at the top of the PR, each noting what to redo if overturned, so the human reviews decisions, not diffs.

**Steal this:** Before your next multi-step feature, write verify.md scenarios that start from a real user entry point and note what the old code does, so a check that could never fail gets caught.

**Go deeper if:** you're the bottleneck on relaying decisions and catching late bugs in agent output, and want a complete, installable spec-verify-deliver loop with cited sources.

> "When the agent struggles, we treat it as a signal: identify what is missing—tools, guardrails, documentation—and feed it back into the repository."

### 4. [GetMintOrg/Engineering: Guardrails for AI coding agents](https://github.com/GetMintOrg/Engineering)
*repo · 5 min · harness design · 9/10*

Rules written in prose (CLAUDE.md) get broken eventually, so when you correct an agent twice on the same thing, turn the rule into a hook, lint rule or CI check that makes the mistake impossible.

**How it works**
- A PreToolUse hook blocks writes to .env files, keys and credentials before the agent touches them.
- A new-test hook requires a @guards tag naming the failure the test catches, and exit code 2 sends the reason back to the agent.
- Custom oxlint rules ban mocking your own modules, narration comments and hand-rolled sleep delays.
- A CI ratchet fails PRs that loosen lint budgets, grow exemption lists or add new disable directives.
- A ship skill takes a change to a green PR with every review thread handled.

**Steal this:** The next time you correct your agent twice for the same mistake, replace the CLAUDE.md line with a PreToolUse hook that exits 2 with a reason, like requiring a @guards comment on new test files.

**Go deeper if:** you're repeating the same corrections to your coding agent and want ready-made hooks, lint rules and CI checks to copy.

> "A rule in prose is a rule the agent will eventually break."

### 5. [Every PR gets an agent review before a human sees it](https://dev.to/avivl/every-pr-gets-an-agent-review-before-a-human-sees-it-440h)
*blog · 8 min · lighter review · 9/10 · 10 Nov*

Reading about 50 PRs a week cold is slow, so each PR first goes to a read-only reviewer agent on a different vendor than the author, and a report reaches the human before the diff.

**How it works**
- Launch one scout agent per PR in its own pane; each can only read the PR and writes report.md locally.
- A binding charter forbids commenting, approving, pushing or merging, and requires findings ordered by severity with file:line citations.
- A fifth spec-review pass sees only the diff, commits and ticket, listing what was asked but not built, built but not asked for, built wrong.
- Pin the reviewer model explicitly, since role overrides skip scouts, and use a different vendor than the code-writing model.
- Cap review rounds at 3 (5 for security changes) and keep a ledger where every finding ends fixed, rejected with reason, or open.

**Steal this:** Before your next batch of PRs, write a read-only review charter (no posting, cited file:line findings, escalate auth and data changes) and run it on a different model than the one that wrote the code.

**Go deeper if:** you're the bottleneck reviewing agent PRs and want the actual charter text, model pinning notes, and tested launcher scripts.

> "The agent can read the PR and nothing else: it can't comment, approve, push or merge."

### 6. [Reflex: an architecture for building mobile apps with agents](https://shopify.engineering/reflex)
*blog · 16 min · verification · 9/10*

Emulators make agent feedback slow, so Reflex runs app logic headlessly and exposes each screen's state and actions as JSON, letting a CLI and one shared test file drive both iOS and Android.

**How it works**
- Keep all non-UI logic in a core module with no UI imports, with platform services passed in through the constructor.
- Give every screen's ViewModel the same shape: actions in, state out, one update function that changes state.
- Add an introspection node per ViewModel exposing a name, state as JSON, and every action, with no conditionals.
- A CLI with ls and do commands reads and drives the focused screen, and the same tests run on both platforms.
- Block all network calls in tests and supply fixtures, so a suite of 1,700+ tests runs in about four minutes.

**Steal this:** Before your next agent-built feature, add a small JSON state-and-actions interface to one screen or service so the agent can inspect it and run a journey test in a terminal without a UI or device.

**Go deeper if:** you're building mobile or UI-heavy apps with agents and want a fast, deterministic feedback loop plus one test suite keeping two platforms in parity.

> "The code is written twice, the tests are written once."

### 7. [How we rebuilt the Shopify app in 12 weeks](https://shopify.engineering/shopify-app-rebuild)
*blog · 14 min · real setups · 8/10*

Agents write code faster than humans can check it, so Shopify rebuilt its mobile architecture, tests and review flow so agents get fast feedback and humans only judge intent.

**How it works**
- Business logic runs without a device, so agents load a ViewModel from a CLI and check state in milliseconds.
- Architecture lives in examples, architecture.md files, lint rules and CI checks that fail when iOS and Android diverge.
- The legacy app serves as the spec; work splits into small checkpoints verified against it, not a written spec.
- An agent does an adversarial review against the guidelines first; humans then review small cross-platform PRs for intent.
- Each day an agent turns that day's review comments into updates to skills and Architecture.md, so one comment becomes a rule.

**Steal this:** At the end of each day, have an agent read all review comments from your PRs and fold the recurring ones into your skills or architecture.md file.

**Go deeper if:** you're scaling agent output and finding that review, CI and merging, not code generation, are now your bottleneck.

> "Agents need more than instructions. They need a way to discover when they are wrong."
